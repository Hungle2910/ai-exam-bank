Schema order follows the existing shared migration stream. School, department and role assignments come first, followed by taxonomy and revisions. Blueprint and generation records can then reference scoped metadata and pinned question revisions. Agree on the event and assignment schema before adding workflow decisions, selected revision pointers or immutable snapshots. M1 coordinates migration ordering with M3 and M4; each owner maintains their module mappings.

Use three milestones to forecast delivery. First, establish the school workflow from Blueprint to approved selection and event decision, including authorization and rollback evidence. Live generation work can proceed in parallel when M2 and M4 have working retrieval and generation configured, but completion needs M3 review and M5 recovery evidence. Then complete the Ministry event and release workflow and run combined acceptance with both event types. Lex, ML experiments and VPN stay behind the existing MVP gate.

M1–M5 should record remaining hours and usable weekly capacity per package, reserve time for migrations, integration and peer review, then recalculate the critical path from prerequisite completion and owner capacity. Update the existing board issues before creating overlapping implementation issues. Confirm revised dates together before replacing the historical Target Date fields.
